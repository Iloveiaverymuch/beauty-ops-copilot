2. Patrons de Composition Multi-Agents : Transfer vs AgentTool

Le choix du patron de composition d'agents dans Google ADK conditionne la fluidité conversationnelle et la maîtrise des coûts :

Pattern ADK Mécanisme d'Exécution Sémantique de Contrôle Cas d'Usage Retail Optimal
LLM Transfer (Handoff) L'agent routeur transfère l'intégralité du tour à un sous-agent spécialisé via un appel d'outil interne. Le sous-agent prend le contrôle total de la conversation et répond directement à l'utilisateur. Changement franc de domaine (ex: passage d'une question générale vers le sous-agent catalogue spécialisé).
AgentTool (Sous-traitance) L'agent principal invoque un sous-agent comme une fonction typée classique et attend son résultat. Le sous-agent s'exécute isolément, synthétise sa donnée, et le contrôle revient à l'appelant. Questions composites (ex: l'agent M365 cherche des infos dans le catalogue pour rédiger un email d'équipe).

3. Stratégie de Context Caching (Gemini & Vertex AI)

Optimisation Économique & Latence : Lors d'un transfert multi-agents, l'ADK réinjecte les prompts système et schémas d'outils. Sans optimisation, chaque transfert renvoie l'intégralité du contexte non-caché. Nous configurons ContextCacheConfig(min_tokens=2048, ttl_seconds=1800) sur l'App ADK : Vertex AI met en cache le préfixe figé des agents. Gain mesuré : -65% sur la facturation des tokens d'entrée et division par deux du TTFT sur les sessions longues.

4. Gestion de Session et Persistance d'État

L'ADK sépare strictement le calcul (Runner stateless) du stockage d'état (SessionService) :

  • Environnement Local / Dev : SqliteSessionService avec un fichier par agent (sessions_advisor.db, sessions_copilot.db) pour tester les reprises sur incident.
  • Environnement Cloud Run (Production) : Remplacement transparent par DatabaseSessionService connecté à Cloud SQL (PostgreSQL), garantissant le scaling horizontal sans perte de contexte.

Enterprise Guardrails

1. Les 3 Niveaux de Sécurité (Defense-in-Depth)

Pour éviter tout comportement déviant en production, l'architecture met en œuvre une défense multicouche rigoureuse :

Niveau Technologie Périmètre & Rôle Action en cas d'Attaque / Non-respect
Niveau 1 : Prompt Google Cloud Model Armor Filtrage en bordure contre les Prompt Injections, Jailbreaks (DAN) et fuites de données personnelles (PII). Interception avant l'appel du modèle. Rejet immédiat avec événement governance_blocked.
Niveau 2 : Outils ADK Native Callbacks
(before_tool_callback)		 Contrôle strict des règles métier (ex: interdiction de remboursement sur produit ouvert sans réaction médicale). Blocage au niveau de l'orchestrateur. L'outil métier ne s'exécute jamais si la condition n'est pas remplie.
Niveau 3 : Plateforme ADK GovernancePlugin & HITL Budgets d'écriture maximaux (ex: 1 écriture/tour), domaines emails autorisés, et validation humaine obligatoire. Interruption de l'agent. Émission d'un événement d'approbation humaine confirmation_required.

Quality & Observability

1. Stratégie d'Évaluation à Double Vitesse (Two-Tier Evals)

Pour allier rapidité de développement et rigueur de production, l'intégration continue sépare l'évaluation en deux étapes étanches :

Tier 1 : Gate Offline Déterministe (< 2 secondes)

Exécuté à chaque git commit et dans chaque PR GitHub Actions. Ne dépend d'aucune API externe et coûte 0 € :

  • 110 tests Pytest : validation des schémas d'outils, calculs volumétriques, retries HTTP avec backoff exponentiel.
  • Moteur de claims SQLite : vérification de l'idempotence des remboursements (UUID de transaction).
  • Contrat SSE Streaming : test de la structure des événements de flux (meta, chunk, usage, done).

Tier 2 : Évaluation ADK Native & Vertex AI Judge

Exécuté avant tout déploiement en staging/production via le runner officiel Google ADK :

  • 7 cas critiques d'entreprise (100% Pass) : détection d'ingénierie sociale, respect des filtres, politique de retour.
  • LLM-as-a-Judge Vertex AI : notation automatisée sur 5 critères (Safety, Faithfulness, Tool Compliance, Tone).
  • Blocage Automatique : seuil minimal imposé de 4.8 / 5.0 pour autoriser le build Cloud Run.
